# MySQL实战45讲学习笔记

本文记录了我在阅读《MySQL实战45讲》过程中对若干细节的补充理解，仅对原文作补充、举例阐述，务必结合原文阅读。

## 01 基础架构

慢查询日志中的 rows_examined 字段，表示这个语句执行过程中扫描了多少行

这里的意思其实是执行器向引擎要了多少次数据，每次只能要一行（因为引擎理论上不负责判断，只负责取一条数据出来交给执行器，执行器去判断这条数据是否符合查询条件）。理论上 rows_examined 字段约等于引擎实际在底层扫描的行数，但现在有 **索引条件下推** 操作，也就是引擎先扫描几行，再根据条件返回一行，所以可能 rows_examined 字段小于实际扫描行数

## 02 日志系统

redo log 是 InnoDB 引擎里的，binlog 是 server 层的

redo log 是用来数据库崩溃，马上重启不丢失数据的（实现细节笔记里不做赘述）；binlog 是用来从上一个全量备份库恢复成当前状态的（或者恢复到之前某一状态从而实现回滚，这里为了举例方便，先假设都是要恢复成当前状态）

二阶段提交的必要性是**从全量备份库通过 binlog 恢复到当前时间点的状态，必须与当前的真实状态一致！！！**

1. **先写 redo log 后写 binlog**。写入 redo log 之后数据库当前真实状态是已更新，如果写 binlog 没成功数据库就崩溃，那么通过 binlog 恢复到当前时间点的状态就是未更新，两个状态不一致（真实状态就是马上数据库重启，此时以 redo log 为准）
2. **先写 binlog 后写 redo log**。写入 binlog 之后数据库通过 binlog 恢复到当前时间点的状态是已更新，但由于写 redo log 前崩溃，当前库真实状态是未更新，两个状态不一致

双阶段提交是按下面三步走的（双阶段指的是引擎写 redo log 两次，写 binlog 是 server 层干的，所以不叫三阶段哈哈）：

1. **阶段一**，引擎将新数据更新到内存，并将操作记录写入 redo log，此时 redo log 处于 prepare 状态
2. 写 binlog
3. **阶段二**，引擎将 redo log 里刚刚事务的状态变成 commit，标记事务已完成

如果数据库在步骤 1 和步骤 2 之间崩溃，重启后此时 binlog 没更新，发现 redo log 处于 prepare 所以回滚。**事务执行失败，但备份库恢复出来的状态和真实状态一致！**

如果数据库在步骤 2 和步骤 3 之间崩溃，此时 binlog 已经更新，发现 redo log **有记录只是处于 prepare** 所以将 redo log 上的事务改为 commit

本质上是写入 redo log 后，处于 prepare 状态是既可以撤销事务，又可以继续提交，根据 binlog 来选择执行哪个操作

## 03 事务隔离

数据库的三个并发异常：

1. **脏读**，事务 A 在执行过程中读取到**未提交的事务 B** 更新后的数据
2. **不可重复读**，事务 A 在执行过程中读取到**已提交的事务 B** 更新后的数据（事务 B 提交前更新的数据读不到）
3. **幻读**，在可重复读（即事务 A 执行过程中，所有事务 B 的更新都看不到，无论事务 B 是否已提交）的情况下，事务 A 执行过程中看到已提交的事务 B **新增或删除**数据（注意前面1、2说的都是更新数据，指的是修改已存在的行，这里是新增或删除行）

事务的隔离级别：

1. **读未提交**，允许脏读、不可重复读、幻读
2. **读已提交**，修复了脏读，通过每次执行 sql 时创建一个 read-view 实现
3. **可重复读**，进一步修复了不可重复读，通过事务开始时创建一个 read-view 实现（准确来说是事务创建后的第一条 SELECT 语句）
4. **串行化**，进一步修复幻读，没有 read-view，直接给数据行上读写锁

read-view 是一个静态的视图，实现方式不是真的把创建视图时数据库里的数据都复制出来（内存直接爆炸），而是通过从需要创建视图时开始记录一个**回滚日志**，每次执行更新操作都会记录对应的一条回滚指令。当要读取视图时，就从当前的真实状态按照回滚日志执行回滚操作到创建视图哪个时间点

回滚日志不需要一直记录，而是一个**滑动窗口**，左指针就是当前最旧的视图，右指针始终是当前时间点的真实状态。一旦最旧的那个视图被销毁，左指针就可以移动

上述机制就叫 **MVCC**

值得注意的是，事务隔离级别是理论上的，InnoDB 的实现有一些区别：

1. InnoDB 默认的隔离级别是可重复读。理论上这一级别允许幻读，但 InnoDB 考虑到主从复制，在这一级别的实现里进一步引入了 Next-Key Lock。这是行锁 + 间隙锁，直接锁住当前读取的数据行和这些行之间的空间，阻塞其他事务的更新、插入和删除
2. InnoDB 的可重复读，对于普通的查询语句采取的仍是**快照读**，不会上 Next-Key Lock。但如果事务里有**当前读**，那就会对这条语句涉及的数据行上 Next-Key Lock。其中 Next-Key Lock 指的是锁的范围（行 + 间隙）。因此 InnoDB 的可重复读，普通查询有快照读，是没幻读问题的；仅存的可能性是，在快照读之后、当前读语句上 Next-Key Lock 前，其他事务新增或删除了数据（见下方例子）
3.  InnoDB 的串行化就是没有快照读，所有普通查询语句都上 Next-Key Lock，并且是 S 锁

**注意，InnoDB 无论哪个事务隔离级别，只要事务里申请了锁，只有到事务提交或回滚才会释放锁！！！**

综合案例（可重复读）：

| 时间轴    | 事务 A (Transaction A)                                               | 事务 B (Transaction B)                                      | 说明 / 内部机制                                                                                         |
| :----- | :----------------------------------------------------------------- | :-------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| **T1** | `BEGIN;`                                                           |                                                           | 开启事务 A                                                                                            |
| **T2** | `SELECT * FROM t WHERE id = 5;`<br>*(返回空)*                         |                                                           | **【快照读】** 事务 A 创建了 Read View，此时表是空的，它什么也没看到。                                                      |
| **T3** |                                                                    | `BEGIN;`<br>`INSERT INTO t (id) VALUES (5);`<br>`COMMIT;` | 事务 B 偷偷插入了一条 `id=5` 的数据，并且**提交了**。                                                                |
| **T4** | `SELECT * FROM t WHERE id = 5;`<br>*(依然返回空)*                       |                                                           | **【快照读】** 事务 A 再次查询，根据 MVCC 的 Read View，它依然看不到事务 B 提交的数据。目前一切正常，防住了幻读。                            |
| **T5** | `UPDATE t SET name = 'wolf' WHERE id = 5;`<br>*(执行成功，影响 1 行)*      |                                                           | **【当前读】🚨 核心转折点！**<br>`UPDATE` 语句是当前读！它不管 Read View，它去底层真实数据里找。结果它真的找到了事务 B 插入的 `id=5`，并且成功把它修改了！ |
| **T6** | `SELECT * FROM t WHERE id = 5;`<br>*(返回了 `id=5, name='wolf'` 的数据)* |                                                           | **【快照读】💥 幻读爆发！**<br>事务 A 再次普通查询，刚才还不存在的数据，现在竟然凭空出现了！                                             |

如果隔离级别变成串行化，那 T2 时刻事务 A 会直接给 id=5 的间隙上 S 锁，T3 时刻事务 B 会之间阻塞直到事务 A 完成或回滚

如果隔离级别仍保持可重复读，且 T3 时刻事务 B 插入数据后没提交，那么**锁没有被释放**，T5 时刻事务 A 会被阻塞

## 04 索引（上）

B 树和 B+ 树的原理详见 [github 博客](https://github.com/wardseptember/notes/blob/master/docs/B%E6%A0%91%E5%92%8CB%2B%E6%A0%91%E8%AF%A6%E8%A7%A3.md)

选择 B+ 树作为 InnoDB 索引模型而不是 B 树的原因：

1. B 树和 B+ 树的一个节点都是一个物理页大小。但 B 树节点包含数据，如果一个表的列数较多，一行数据就比较大，对 B 树来说一个物理页能装下的索引比 B+ 树少，树会更高
2. B 树对范围搜索不友好，要在上下层之间中序遍历节点。InnoDB 实现的 B+ 树在叶子节点这一层做了双向链表，可以在最底层直接顺序遍历返回结果
3. 查询性能稳定。在 B 树上搜索，可能根节点直接命中，也可能直到叶子节点才命中；而 B+ 树则都要到叶子节点才返回结果，效率稳定

**留意回表机制！这是重点**

PS：如果查询语句是根据二级索引查询，但要查的数据列已经全部包含在二级索引这棵 B+ 树里（只查二级索引 + 主键），那么不会触发回表，这叫**覆盖索引（Covering Index）**

## 05 索引（下）

关于 `select * from T where k between 3 and 5` 这个例子，server 层和引擎层分别干的事：

1. server 层向引擎要 k=3 的数据，引擎到 B+ 树里搜素找到这一条
2. 引擎对 k=3 取出来的主键进行回表
3. server 层向引擎要**下一条数据**，引擎顺着链表找到 k=5 
4. 引擎对 k=5 取出来的主键进行回表
5. server 层再向引擎要**下一条数据**（因为可能还存在多条 k=5），引擎顺着链表找到 k=6 发现不满足条件，返回"没有下一条数据"，结束。因此 server 层扫过两行，但引擎扫过三行

注意，索引下推可以用于减少回表次数

"01 基础架构"笔记里有提到，索引下推会导致 server 层的扫描行数与引擎层不一致。这是因为 server 层的扫描行数其实是调用引擎获取下一行数据的次数。以前引擎会如实的按照第一个查询条件查数据出来，交给 server 层，server 层判断不符合后续条件，丢弃然后调用接口获取下一条数据。现在如果后续条件也包含在索引里，引擎会顺便判断，这就导致 server 层需要调用接口的次数变少。

## 20 幻读是什么

这里要对 **"03 事务隔离"里 Next-Key Lock 进行补充**

首先，Next-Key Lock = 行锁 + 间隙锁，而**只有行锁有 S 锁和 X 锁的概念**，间隙锁只负责 **"不允许其他线程往这个间隙插数据"**，所以多个线程可以对同一个间隙上间隙锁，这不会堵塞，**除非有线程要往这个间隙插数据，那它得等到所有间隙锁 unlock**

而对于 InnoDB 的默认隔离级别可重复读，事务里的一句当前读 `SELECT * FROM T WHERE field=xxx FOR UPDATE` 要分为以下几种情况来上锁

1. `field` 字段没有索引，不用管 xxx 是否存在，直接全表所有间隙上间隙锁，所有行上 X 锁，简单粗暴，相当于锁全表
2. `field` 字段有索引，但索引是普通的可重复索引
   - `field=xxx` 存在，那就这一行上 X 锁，前后间隙上间隙锁（怕插入相同 field 值的新数据行，毕竟**索引可重复**）
   - `field=xxx` 不存在，那就 xxx 所在这个间隙上间隙锁
3. `field` 字段有唯一索引，甚至**主键索引**
   - `field=xxx` 存在，那就这一行上 X 锁，无间隙锁（不用担心插入相同 field 值的新数据行）
   - `field=xxx` 不存在，那就 xxx 所在这个间隙上间隙锁

如果语句换成 `SELECT * FROM T WHERE field=xxx LOCK IN SHARE MODE` 就把上面三种情况里 X 锁替换成 S 锁

## 21 锁怎么这么多

**必须记住锁只能上在访问过的对象上！！！**

_注意覆盖索引的特殊情况：_
- 如果是 `LOCK IN SHARE MODE` 且用到了覆盖索引，锁只会加在这个辅助索引上，此时其他事务通过主键依然能更新该行的其他字段。
- 如果是 `FOR UPDATE`，即使是覆盖索引查询，InnoDB 也会自动去把对应的主键索引记录也加上 X 锁，此时其他事务无法更新该行。

**结合原文案例三、案例四：** 等值查询，间隙的右边界会退化；而范围搜索的右边界不会退化，保持左开右闭！！！

**结合原文案例六：** 普通可重复索引的最底层叶子节点会根据主键来排序！！所以同一个索引值内部也有顺序，自然也有间隙。等值查询右边界退化、范围查询右边界不退化等，仍作用于这些相同索引值的间隙。
