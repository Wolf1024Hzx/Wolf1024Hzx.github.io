# Redis 单线程模型

## IO 多路复用

每次都开一个新的线程去处理 1 个 IO 是非常奢侈的，因为线程切换的成本并不低。所以尽可能希望一个线程能够处理多个 IO，这就叫 **IO 多路复用**

Linux 内核里对 IO 多路复用有以下三个实现方案，性能依次提升

### select

最古老、简单粗暴的方法。每个线程都维护一张自己要处理的 IO 列表（数组实现，长度为 1024，也就是说一个线程最多处理 1024 个 IO）。需要执行 IO 事件时就将整个列表提交给内核，然后阻塞。内核完成其中的事件后，唤醒对应线程

**缺点：** 每次都要把整个列表复制给内核，内核顺着列表查询时间复杂度是 O(N)

### poll

和 select 几乎一样，只是数组换成链表，没有数量限制

### epoll

每个线程都可以调用 `epoll_create()` 接口，在内核维护一棵当前线程要处理的 IO 事件组成的**红黑树**（代替 select 的数组和 poll 的链表，并且直接维护在内核，不需要拷贝）

IO 事件执行完毕后，触发中断。内核会根据数据包里的端口信息找到对应的进程，将结果放入其对应线程的就绪队列，唤醒正在阻塞等待结果的该线程

**优点：** 程提交时间效率高，因为用的是红黑树；不需要把整个列表复制给内核；唤醒后直接在就绪队列中看到是哪个事件已完成，不需要遍历整个事件列表，时间复杂度 O(1)

## Redis 主事件循环

Redis 的主事件循环是单线程的，而它能够处理多个网络 IO 请求，就是因为使用了上面提到的 IO 多路复用里的 epoll。

在事件循环开始前，Redis 启动时进行初始化：

1. 先 `epoll_create()` 准备好红黑树（需要完成的事件清单），并创建 socket
2. 通过 `bind()` 绑定端口，`listen()` 监听 socket
3. 将 socket 放进 epoll 红黑树里，表示有请求（**连接事件**）来了就 cpu 中断，进内核处理（从网卡拿数据），拿到数据就放入就绪队列

初始化完成后，会不断进行下面这个主事件循环：

1. 先看看发送队列是否为空，有的话就拿出来执行，也就是往客户端发结果。如果这个过程中网络拥堵，那就继续把这个任务塞回到发送队列（因为没完成），然后往 epoll 上挂一个**写事件**（表示等内核告诉 Redis 这个任务可以继续写了再在下次事件循环中执行）
2. `epoll_wait()` 主线程阻塞，等待内核用某个事件唤醒
3. 如果唤醒主线程的是**连接事件**，那就往 epoll 上挂一个**读事件**，等客户端发指令；如果唤醒主线程的是**读事件**，执行客户端传过来的指令。得到结果后不会马上发送给客户端，而是丢进发送队列；如果唤醒主线程的是**写事件**，继续发送这个任务没发完的数据，对网络拥堵的处理同第一步
4. 回第一步

## 跳表

定义如下：

```c
typedef struct zskiplistNode { 
	//Zset 对象的元素值 
	sds ele; 
	
	//元素权重值 
	double score; 
	
	//后向指针 
	struct zskiplistNode *backward; 
	
	//节点的level数组，保存每层上的前向指针和跨度 
	struct zskiplistLevel { 
		struct zskiplistNode *forward; 
		unsigned long span; 
	} level[]; 
} zskiplistNode;

// 头节点
typedef struct zskiplist { 
	struct zskiplistNode *header, *tail; 
	unsigned long length; 
	int level; 
} zskiplist;
```

## 跳表插入

跳表插入原文没讲清楚，这里详细说明一下

先要先找到新的节点插在哪里。这里就是要根据上面提到的节点顺序比较规则，找到"当前位置小于待插入节点，后一位为空或后一位大于待插入节点"的那个节点。找的过程中会持续用到一个 update[最大层数] 数组。这个数组用于**记录每一层在尝试这个节点时，最后走到哪，也就是记录每一层上待插入节点的前驱节点是谁！！！**

一边记录一边搜索，走到最下一层，确认插入位置后，就开始进行原文中提到的，每次以 1/4 的概率增长层数

确定层数后，就使用 update 数组获取需要的前驱节点，然后修改前驱节点对应层数的 forward，更新 span。插入完成

# Pipeline

Redis 的 Pipeline 和事务没什么关系。这是一个客户端优化的操作，将多条指令合并在一起发给 Redis 服务端，这样就不用等待 Redis 服务端的响应才发下一条请求

# 事务

Redis 是有事务这个概念的，也就是事务执行过程中一定没有其他事务的指令插入（毕竟是单线程模型）

但是 Redis 事务**不支持回滚！！！**，如果事务语句有语法错误，那 Redis 将这条指令写入缓冲队列时就会报错停止，不执行事务；但如果是运行过程中出错，**事务直接结束无法回滚**

## RDB

RDB 是全量快照，通过**写时复制（Copy-On-Write, COW）**，fork 一个子进程，让内核按需复制内存页来完成

值得注意的是，上面这个是 bgsave 命令做的。实际上 Redis 还有一条 save 命令，直接在主线程上开始全量快照，会造成堵塞

而且配置文件里的 `save [时间间隔/秒] [时间间隔内修改数据次数]` 满足这个条件时触发的是 bgsave。神奇

**注意：** 小林 coding 里写 bgsave 子进程访问的是副本，这是不对的。按需复制的原理是，fork 时父子进程的页表是一样的，指向一样的物理内存，然后内核把这块物理内存标记为**只读**。父进程尝试写入时触发**缺页中断**，内核复制该虚拟内存地址对应的物理块到一个新的块，然后修改父进程的页表，让父进程修改**新的物理块**。

# Redis 集群

## 分片算法

一台机器的内存装不下，需要多台机器，每台机器上的 redis 就是一个分片

既然有分片的概念，那么根据 key 读取或修改 value 就需要知道这个数据在哪个分片上。有以下三个算法可以解决这个问题：

1. **哈希取余**
2. **一致性哈希（Consistent Hashing）**
3. **哈希槽（Hash Slot）**

### 哈希取余

最粗暴的方法，假设有 N 个分片，当前数据就归属于 `hash(key) % N` 这个分片。缺点也很显然，增加或者减少分片数量的时候，所有余数都会失效，所有缓存都要移动，造成雪崩

### 一致性哈希（Consistent Hashing）

这个算法就是为了解决哈希取余一旦增减分片数量，所有缓存失效的问题。目标就是，增减分片数量时缓存数据尽可能不移动

首先将 0 到 $2^{32}-1$ 围成一个圈，共 $2^{32}$ 个点。然后使用分片的 ip 地址 / MAC 地址 / 主机名 / 随便一个集群内的唯一标识，计算分片在圈上的位置 `hash(addr)` % $2^{32}$。然后查询数据位置的时候，先计算 key 在圈上的落点 `hash(key)` % $2^{32}$，然后从落点顺时针找到的第一个分片，就归属于它

新增分片时，只需要移动**属于某个分片的一部分数据**，比如在分片 1 和分片 2 之间插入一个分片 A，分片 A 恰好在 1 和 2 中间（方便起见的假设），那么只有落在 1 和 2 之间靠近 1 那一半的数据（原本属于分片 2）需要移动到分片 A，落在剩下一半的数据仍留在分片 2，如下图所示。删除分片时同理。

![一致性哈希](/img/Redis学习笔记/一致性哈希.png)

可以很容易发现，一致性哈希有个很大的问题是分片映射到的位置是不均匀的，这就会导致不同分片上缓存的数据量不均匀。

为了解决这个问题，**虚拟节点**诞生了。原理就是既然分片在圆环上不均匀，那就给每个分片都生成几十上百个虚拟节点，指向自己，但分布在圆环上的不同位置。缓解了数据不均匀的问题。

> 但是引入了虚拟节点后的一致性哈希映射关系不够灵活，面对一些定制化需求又不太合适。比如要将同一个用户的不同缓存数据放在同一个分片上。因此引出 Hash Slot

### 哈希槽（Hash Slot）

集群启动时，无论有多少个分片，都固定集群里有 16384（$2^{14}$） 个 slot，均匀分布在所有分片上：

- 分片 A 负责保管 0 ~ 5460 号 slot
- 分片 B 负责保管 5461 ~ 10922 号 slot
- 分片 C 负责保管 10923 ~ 16383 号 slot

数据来了先计算 `CRC16(key)`，这是根据 key 算出一个 16 位数字。然后 `CRC16(key) % 16384` 获取 slot 号，就可以直接定位到对应的分片。

key -> slot 序号这个映射关系是不变的，因为 CRC 算法是固定的。增减分片数量时，每个分片上的一部分 slot 都需要移动，但至少不需要所有数据都移动。

- **既然 CRC 可以生成 $2^{16}$ 个数，为什么分片数量是 $2^{14}$ 而不是 $2^{16}$?**
  1. 够用就行，官方推荐的节点最大数量是 1000，16000+ 的分片数量已经够用了
  2. 集群里，节点互相之间会定期发送心跳包沟通状态，其中就包括了各个 slot 的状态。每个心跳包都用 bitmap 存整个集群的所有 slot 状态，一个 slot 对应 1 bit，$2^{16}$ bit = 8KB，造成网络带宽浪费
- **前文提到的"要将同一个用户的不同缓存数据放在同一个分片上"是如何在 HashSlot 里解决的？**
  1. 通过 Hash Tag 机制。如果 key 里面存在一对大括号 `{}`，redis 会根据大括号内的字符串来计算 Hash Slot。例如 `{userID:100}:profiles` 和 `{userID:100}:orders` 计算出来的 Hash Slot 是一样的，必然分配到同一个分片上
