# InnoDB 可重复读下幻读为何仍会爆发

## 先说结论

InnoDB 的可重复读通过 MVCC 实现快照读，确实能防止大部分幻读。但当一个事务中既有快照读又有当前读时，幻读可能在两者之间的时间窗口爆发。

## MVCC 机制回顾

read-view 是一个静态的视图，实现方式是通过**回滚日志**。每次执行更新操作都会记录对应的一条回滚指令。当要读取视图时，就从当前的真实状态按照回滚日志执行回滚操作。

回滚日志是一个**滑动窗口**，左指针是最旧的视图，右指针是当前状态。视图销毁后左指针移动。

**但 MVCC 只作用于快照读（普通 SELECT）。**

## 当前读 vs 快照读

- **快照读**：普通 SELECT，基于 Read View 看到的是事务开始时的数据状态
- **当前读**：SELECT ... FOR UPDATE、UPDATE、DELETE 等，直接读取底层真实数据

InnoDB 的可重复读对当前读会加 Next-Key Lock（行锁 + 间隙锁），防止其他事务插入数据。**但锁是在执行当前读时才加的，在此之前的时间窗口是暴露的。**

## 幻读爆发的完整时间轴

| 时间轴 | 事务 A | 事务 B | 说明 |
|:-----|:------|:------|:----|
| **T1** | `BEGIN;` | | 开启事务 A |
| **T2** | `SELECT * FROM t WHERE id = 5;` *(返回空)* | | **【快照读】** 创建 Read View，表是空的 |
| **T3** | | `BEGIN; INSERT INTO t (id) VALUES (5); COMMIT;` | 事务 B 插入并提交 |
| **T4** | `SELECT * FROM t WHERE id = 5;` *(返回空)* | | **【快照读】** MVCC 仍看不到事务 B 的数据，防住了幻读 |
| **T5** | `UPDATE t SET name = 'wolf' WHERE id = 5;` *(影响 1 行)* | | **【当前读】** UPDATE 不管 Read View，直接去真实数据里找，找到了事务 B 插入的 `id=5`，并成功修改 |
| **T6** | `SELECT * FROM t WHERE id = 5;` *(返回数据)* | | **【快照读】** 刚才还不存在的数据，现在凭空出现了 |

**关键转折点在 T5**：UPDATE 是当前读，它绕过了 MVCC 的 Read View，直接操作真实数据。事务 B 插入的数据被"激活"并加入事务 A 的 Read View。

T5 之后事务 A 的 Read View 里就有了 `id=5` 这条记录，所以 T6 的快照读能看到它。这就是幻读爆发。

## 为什么锁没防住？

T2 是快照读，**不加锁**。Next-Key Lock 只有在当前读时才加。

时间窗口：T2（快照读，无锁） → T3（事务 B 插入） → T5（当前读，才加锁）

事务 B 的插入正好落在 T2 和 T5 之间的无锁窗口。

## 解决方案

1. 一开始就用当前读：`SELECT * FROM t WHERE id = 5 FOR UPDATE`，直接加锁
2. 事务 B 插入后不提交，T5 的 UPDATE 会阻塞等待锁释放
