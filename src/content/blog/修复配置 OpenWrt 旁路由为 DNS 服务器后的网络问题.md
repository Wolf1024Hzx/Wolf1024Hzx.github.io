## 异常现象描述

在将 OpenWrt 设置为局域网内的 DNS 服务器后，手机连接路由器 WiFi 出现了很诡异的现象：
* 能正常访问：微信、哔哩哔哩、小红书等少数 App。
* 网络异常/极慢：知乎、豆包、京东等绝大部分应用几乎无法加载，偶尔才能收到响应。

推测该问题与 OpenWrt 上运行的 OpenClash 有关，特别是开启了 Fake-IP 的 TUN 模式

## 原理分析：TUN 模式与 Fake-IP

1. **TUN 模式（虚拟网卡）**：
   - TUN 模式会在系统内创建一张虚拟网卡。来自客户端的流量会被路由到这张虚拟网卡，然后虚拟网卡将流量移交给 Mihomo 内核处理；Mihomo 发起请求后，再将响应通过虚拟网卡交还给对应进程。
   - 解决了应用层不读取系统代理配置、系统代理对底层协议不生效之类的问题，确保流量都能被代理。

2. **Fake-IP**：
   当客户端进程发起域名请求时：
   * 请求先经虚拟网卡交给 Mihomo 内核。
   * Mihomo **立即返回一个假 IP** 给客户端，并在代理服务器那头进行真正的 DNS 解析获取真 IP。
   * 客户端拿到假 IP 后，尝试向该假 IP 发起真实的网络连接。
   * 连接再次被虚拟网卡拦截，Mihomo 将其匹配到远端的真 IP，完成数据转发。
   * 可以防止 DNS 污染之类的。

## 异常原因

其实就是手机的 DNS 配置为 OpenWrt，但默认网关仍然是小米路由器。

除了之前配置好的 `*.wolfden.website` 子域名会被 OpenWrt 拦截解析到 Nginx Proxy Manager 之外，其他公网域名的解析请求都会命中 OpenClash，被返回一个 Fake-IP。

简单画个拓扑图：

```text
【错误的网络拓扑与流量走向】

[普通手机/平板] 
   │
   ├── 1. DNS 请求 (zhihu.com) ──> [OpenWrt (DNS)] ──> Mihomo 返回 Fake-IP (如 198.18.0.5)
   │
   └── 2. 业务流量 (发往 198.18.0.5) ──> 【网关：小米路由器】 
                                            │
                                            └──> 尝试将 198.18.0.5 转发至公网 ──> 丢弃/无响应 ❌
```

手机拿到 Fake-IP 后，由于网关是小米路由器，手机会直接把发往 Fake-IP 的数据包丢给小米路由器。小米路由器根本不知道 `198.18.0.5` 是个啥玩意，尝试丢到公网上，导致客户端无法访问服务。

*（猜测微信等少数 App 能连上是因为内部有 IP 直连/备用 HTTPDNS 机制，绕过了系统的 DNS 解析。待验证)*

## 解决方案

解决方案其实很简单：让不需要走代理的设备，不拿到 Fake-IP

只需要配置 OpenClash 的白名单：
1. **仅允许网关指向 OpenWrt 的设备走代理**：其实只有 PVE 里的 Ubuntu 虚拟机，就是HomeLab 里的服务节点，将它的 IP 加入 OpenClash 的白名单，就会拿到 Fake-IP，流量也就能交由 OpenWrt 的 TUN 网卡处理。
2. **普通局域网设备旁路化**：手机、普通电脑之类的设备不加入白名单。这样向 OpenWrt 请求 DNS 时，不会被 Mihomo 劫持返回 Fake-IP，而是由 OpenClash 丢给小米路由器，执行正常 DNS 解析获取真实 IP。白名单外的设备虽然不走代理，但依然会被 OpenWrt 将 `wolfden.website` 的几个内网服务子域名导向内网 NPM。

```text
【修复后的网络拓扑与流量走向】

[HomeLab 服务节点] (白名单内，网关为 OpenWrt)
   ├── 1. DNS 请求 ──> [OpenWrt] ──> 返回 Fake-IP
   └── 2. 业务流量 ──> [OpenWrt (网关)] ──> 命中 TUN 虚拟网卡 ──> Mihomo 接管代理 ✅

[普通手机/设备] (白名单外，网关为小米路由器)
   ├── 1. DNS 请求 ──> [OpenWrt] ──> [小米路由器] ──> 返回 真实公网 IP (或 NPM 内网 IP)
   └── 2. 业务流量 ──> [小米路由器 (网关)] ──> 正常直连公网 (或内网穿透) ✅
```

## 补充注意（2026-07-23 实锤）：白名单内的 Ubuntu 节点访问自身域名会走进代理

**现象**：在 Ubuntu 服务节点（192.168.31.119，OpenClash 白名单内）上解析 `*.wolfden.website` 任意名字，返回的都是 Mihomo fake-ip（198.18.x.x，TTL=1），不是主机名映射里的 192.168.31.119；https 访问会失败（mihomo 反查域名在公网 NXDOMAIN，链路两头断）。

**实锤证据（2026-07-22 晚 dig 排查）**：

- git / homepage / test123 / apex 四个名字全部返回 fake-ip、TTL=1（mihomo 招牌特征）；连明确配过映射的 homepage 也不例外 → 查询根本没走到 dnsmasq 的映射逻辑，OpenClash 的 DNS 劫持顺序在映射匹配之前。
- 对照组 @192.168.31.1（小米路由器）：子域名 NXDOMAIN、apex 正常公网解析 → 问题只出在 OpenWrt 的劫持链路。
- 白名单以外的设备（手机/电脑）用域名访问完全正常：它们的 DNS 走 dnsmasq 正常流程，映射生效。**全局域网只有白名单内这台 VM 域名访问是坏的。**

**本质（白名单悖论）**：这台 VM 既要走代理访问外网（DNS 必须被 Mihomo 接管），又要直连内网域名（需要 dnsmasq 映射生效）——两个需求在同一个 DNS 链路上互斥，代理赢了，内网域名就输了。

**决定（2026-07-23）：不修复，维持"VM 上用 IP"规则**：

- 备选修法（mihomo 自定义 hosts，或 fake-ip-filter + nameserver-policy）都要在 Clash 里把内网域名映射**再维护一份**，与 OpenWrt 主机名映射形成两处配置，必然漂移——不修。
- 规则：**在这台 VM 上访问本机服务，一律使用 `127.0.0.1:端口` 或 `192.168.31.119:端口`，不要使用 `*.wolfden.website` 域名**；未来 k3s 的 Pod 访问本机依赖同理（Pod 的 DNS 也走这台 VM 的出口）。域名解析是给白名单以外的内网设备用的。
- 实例：2026-06 配置 Gitea act_runner 时，用 `https://git.wolfden.website` 注册报 "Cannot ping the Gitea instance server"，改用 `http://127.0.0.1:3001` 立刻成功。当时归因于 NPM 的 RPC 不兼容，实际根因就是本条。
