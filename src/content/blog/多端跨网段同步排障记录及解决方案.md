## 先写结论

深圳大学校园网某处防火墙/路由/交换机部署了深度包检测（DPI）。其策略允许普通的网页读取（HTTP GET），但会对跨网段的大型文件上传（HTTP PUT/POST 明文传输）进行审查和拦截。

## 0. 初始状态与网络拓扑

* **服务端（实验室）：** Ubuntu 存储节点、win11 工作站连接千兆交换机，交换机接墙上网口。
* **客户端（宿舍）：** 主力台式机、笔记本、手机等，连接宿舍路由器。宿舍的旁路由 OpenWrt 只作局域网内 DNS 拦截（DHCP 下发的网关 ip 还是指向路由器），而今晚的折腾与域名、DNS 等无关，因此不用考虑旁路由。
* **已知现象：** 实验室与宿舍处于不同网段，但网络拓扑属于同级。配置宿舍路由器端口转发后，双向 RDP（远程桌面）畅通。

---

## 1. 第一阶段：Syncthing 部署与发现异常

最初尝试使用 Syncthing 进行文件夹同步：

1. **前端配置保存无响应：** Web UI 中点击保存按钮窗口直接关闭，配置未生效，且无弹窗报错。在控制台中检查，发现修改配置的请求 net::ERR_EMPTY_RESPONSE。此时我的笔记本是 **开启了 clash 的 TUN 模式**。
2. **网络模式修改：** 怀疑是 Docker Bridge 网络的 MTU 限制或吞包，将网络模式切换为 `host`，结果和第一点一致。
3. **尝试原生安装：** 测试了基于 APT 的 Ubuntu 原生安装。手机和电脑端配置无法保存的现象依然存在。初步判断 Syncthing 在当前网络链路中不可用，卸载。

---

## 2. 第二阶段：Obsidian + Remotely Save (WebDAV / S3)

转向应用层的 Obsidian 第三方同步插件方案。

1. **WebDAV (基于 Alist) 测试：** 手机端使用 CX 文件管理器可正常访问 Alist 的 WebDAV 并读取目录。但在 Obsidian 中配置 Remotely Save 插件进行同步测试时，持续报错 `net::ERR_EMPTY_RESPONSE`。（猜测同步测试也是在尝试上传文件。而手机 CX 文件管理器下载文件是正常的，但同样无法上传文件）
2. **MinIO (S3 协议) 测试：** 部署 MinIO 容器，在 Obsidian 端将协议切换为 Amazon S3。MinIO 容器日志中无任何 API 请求被拒绝的记录，说明请求未到达业务层。报错和前面一致。

---

## 3. 第三阶段：网络层拦截验证 (Root Cause Analysis)

为排除客户端软件（Obsidian/Chromium 内核）干扰，使用 Windows 原生命令行工具直接发包测试。

**实验 1：Curl 裸发 PUT 请求**
```cmd
curl -v -u 账户:密码 -T test_upload.txt http://192.168.45.229:5244/dav/wolf-storage/test.txt

* Trying 192.168.45.229:5244...
* Established connection to 192.168.45.229 (192.168.45.229 port 5244) from 192.168.31.22 port 63825
* using HTTP/1.x
* Server auth using Basic with user 'admin'
> PUT /dav/wolf-storage/test.txt HTTP/1.1
> Host: 192.168.45.229:5244
> Authorization: Basic YWRtaW46V29sZjEwMjQh
> User-Agent: curl/8.18.0
> Accept: */*
> Content-Length: 15
>
* upload completely sent off: 15 bytes
* Recv failure: Connection was reset
* closing connection #0
curl: (56) Recv failure: Connection was reset
```
* **输出分析：** TCP 握手成功，19 bytes 的文件载荷已完整发出 (`upload completely sent off: 19 bytes`)。紧接着底层抛出 `Recv failure: Connection was reset`。
* **结论：** 服务端未主动断开连接，而是中间网络设备伪造了 TCP RST 包，强制阻断了连接。

**实验 2：Tracert 路由追踪**
```cmd
tracert 192.168.45.229

  1     1 ms     1 ms     1 ms  192.168.31.1
  2     3 ms     3 ms     3 ms  172.30.48.1
  3     6 ms     *        *     192.168.255.107
  4     6 ms     5 ms    11 ms  192.168.255.41
  5     *        *        *     请求超时。
  6     3 ms     3 ms     2 ms  192.168.45.229
```
* **输出分析：** 在到达目标服务器（第 6 跳）之前，第 5 跳显示 `* * * 请求超时`。
* **结论：** 链路中存在配置了隐身模式的安全网关或核心交换机。

**最终定位：** 校园网核心防火墙部署了深度包检测（DPI）。其策略允许普通的网页读取（HTTP GET），但会对跨网段的大型文件上传（HTTP PUT/POST 明文传输）进行审查和拦截。
* 当直接连接时，防火墙发送 RST 包，浏览器表现为 `ERR_CONNECTION_RESET`。
* 当开启代理软件的 TUN 模式时，虚拟网卡吞掉了异常的 RST 包，导致浏览器等待超时，表现为 `ERR_EMPTY_RESPONSE`。

---

## 4. 解决方案

用 **RDP 绕过 + Syncthing TLS 加密直连** 的方案，成功实现绕过校园网 DPI 检测，完成跨网段文件同步

1. 既然实验室工作站和存储节点连在同一个交换机上，那用实验室工作站访问存储节点就不会有 "Web UI 上无法修改 Syncthing 配置" 的问题！！！而 RDP 远程桌面连接不会被校园网拦截
2. 在 Ubuntu 存储节点上通过 Docker 部署 Syncthing 容器，映射相关端口
3. 从宿舍远程桌面到实验室工作站，在 Win11 工作站的浏览器中访问存储节点的 Web UI 修改配置，添加宿舍各设备的 id 并配置共享文件夹
4. 宿舍客户端与实验室节点处于不同网段，原生的 UDP 局域网发现（端口 21027）失效。因此在宿舍的 Syncthing 客户端中添加存储节点时，不用 `dynamic` 动态发现，写死目标 IP 地址：`tcp://192.168.45.229:22000`。
5. 宿舍客户端直接向存储节点发起 TCP 连接。Syncthing 节点间实际传输使用的是 TLS 双向加密的块交换协议（BEP），中间防火墙无法解析出明文 HTTP PUT/POST 特征，校园网无法拦截，搞定。

## 5. 安卓端相册同步备份方案 

为了实现手机照片向 Ubuntu 存储节点的静默增量备份，在安卓端进行了以下配置：

* **客户端选择：**  Syncthing-Fork。相比官方基础版，该分支版本对高版本 Android 的分区存储机制适配更好，而且支持基于 Wi-Fi SSID 和电源状态的同步触发逻辑自定义。
* **单向增量备份配置：** 手机端设置为仅发送。进入存储节点 Web UI 的全局高级配置 (`操作 -> 高级 -> Folders -> [对应相册文件夹]`)，开启底层的 **`Ignore Delete`** 功能。
